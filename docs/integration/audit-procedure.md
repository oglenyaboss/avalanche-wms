# Процедура аудита: сверка БД с цепью

**Первоисточник:** [ADR-0001 «Подписанные складские действия»](../adr/0001-signed-actions.md) (§4 — `detailsHash`, §8 — как аудитор читает цепь).

Идея: аудитор не доверяет ни WMS, ни адаптеру. Детали и соль берутся из доменных таблиц WMS, цепь читается напрямую, хеш деталей пересчитывается, подпись проверяется заново. Инструментов два: CLI-сверка `wms/cmd/audit` и страница `/audit` для роли AUDITOR.

---

## 1. CLI: `wms/cmd/audit`

Сверка подписанных складских действий: БД (`warehouse_actions` + доменные таблицы) против цепи (`SignedMappingWMS`, `ConsortiumRegistry`). Код: `wms/cmd/audit`, `wms/internal/audit`.

### Что сверяется на каждое действие

1. **Тип действия** — тип в БД против `ActionApplied` в цепи.
2. **Хеш деталей** — `detailsHash` пересчитывается из доменных таблиц (соль из `warehouse_actions.salt`), а не из копии деталей: подмену ячейки в `putaways` или состава заказа так не спрятать.
3. **Список товаров** — множество `itemId` в БД против набора товаров в цепи (по `ItemMoved`).
4. **Подписант** — `keyId` и организация в БД против `ActionApplied`.
5. **Подпись** — из calldata транзакции берётся assertion, challenge пересчитывается, WebAuthn-подпись проверяется по правилам контракта (`VerifyOnChain`), ключ — из `ConsortiumRegistry.getKey`.

### Статусы этапа и типы расхождений

Статус этапа: `APPLIED`, `REJECTED` (с кодом причины из `ActionRejected`), `PENDING` (в БД, ещё не подтверждён), `MISSING_ON_CHAIN`, `MISSING_IN_DB`.

Расхождение фиксируется как finding с типом (`wms/internal/audit/audit.go`):

| Kind | Значение |
|---|---|
| `MISSING_IN_DB` | действие есть в цепи, но нет в БД |
| `MISSING_ON_CHAIN` | действие есть в БД, но не дошло до цепи (не PENDING/SENT) |
| `TYPE_MISMATCH` | тип действия в БД не совпадает с цепью |
| `DETAILS_HASH_MISMATCH` | пересчитанный хеш деталей не совпал (или доменная строка отсутствует/несогласована) |
| `ITEMS_MISMATCH` | наборы товаров в БД и в цепи различаются |
| `SIGNER_MISMATCH` | `keyId`/организация подписанта не совпадают |
| `BAD_SIGNATURE` | подпись не проходит проверку |

### Запуск

```bash
cd wms
RPC_URL=<rpc> CONTRACT_ADDR=<signedmappingwms> REGISTRY_ADDR=<registry> \
  go run ./cmd/audit product <product-uuid|qr-code>   # один товар
go run ./cmd/audit action <action-uuid>               # одно действие
go run ./cmd/audit all                                # вся БД против цепи
```

- Флаг `--json` перед подкомандой отдаёт отчёт JSON; код возврата `1`, если есть расхождения (удобно для CI).
- Окружение: `RPC_URL`, `CONTRACT_ADDR`, `REGISTRY_ADDR` (каждое — или `<NAME>_FILE`); БД: `DB_HOST`, `DB_PORT`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`.
- Отдельной make-цели у CLI нет — запускается из каталога `wms/`.

## 2. Страница `/audit` (роль AUDITOR)

Веб-страница для аудитора (`frontend/src/pages/audit`; в навигации доступна ролям `AUDITOR` и `ADMIN`). Товар ищется по QR-коду или `product_id`.

### Что показывает страница

По каждому подписанному действию товара — строка со статусом и четырьмя проверками «✓/✗/—»:

- **Статус:** «В цепи» / «Отклонено (код N)» / «Ожидает записи в цепь» / «Нет в цепи» / «Нет в БД»;
- **Исполнитель** и **организация** — кто подписал и от чьего имени;
- **Время блока** — момент применения в цепи;
- проверки: **хеш деталей**, **подписант**, **товары**, **подпись** — ✓ совпадает, ✗ не совпадает, — не проверялся (например, у отклонённого действия).

### Откуда какие данные

- **БД** — только из бэкенда: `GET /audit/products/{key}` (`wms/internal/audit/http.go`). Эндпоинт отдаёт исключительно данные БД: действия товара, соль и детали, пересчитанные из доменных таблиц; ничего из цепи он не читает.
- **Цепь** — браузер читает **напрямую с RPC-узла**, минуя бэкенд (`frontend/src/features/audit/api/chainReader.ts`), по схеме ADR-0001 §8:
  1. `getLogs(ItemMoved, itemId)` → список `actionId` товара;
  2. `getLogs(ActionApplied / ActionRejected)` → `keyId`, организация, `detailsHash`, номер блока;
  3. `registry.getKey(keyId)` → публичный ключ и организация;
  4. `eth_getTransactionByHash` → декодирование calldata `applyActions` → проверка WebAuthn-подписи в браузере (WebCrypto P-256);
  5. `detailsHash` пересчитывается в браузере из БД-деталей и сравнивается с цепью.

  Поэтому RPC-узел должен отдавать транзакции по хешу и логи — обычный полный узел отдаёт; кросс-доменные запросы браузера к узлу разрешает avalanchego (`http-allowed-origins`, по умолчанию все origin; в `deploy/subnet/node-config.json` не переопределён).

### Настройки страницы

RPC-узел и адрес контракта задаются на самой странице и запоминаются в браузере (`localStorage`); значения по умолчанию берутся из переменных окружения сборки фронтенда `VITE_AUDIT_RPC_URL` и `VITE_AUDIT_CONTRACT_ADDR` (`frontend/src/shared/config/env.ts`). Адрес `ConsortiumRegistry` отдельно не вводится — страница читает его вызовом `registry()` у `SignedMappingWMS`.

CLI и страница проверяют одно и то же разными путями: CLI работает внутри контура (RPC + БД), страница — снаружи, только RPC и один read-only эндпоинт WMS.
