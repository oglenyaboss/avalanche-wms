# Гео-распределённый блокчейн-слой: корневой анализ пропускной способности

> Почему гео-сеть коммитит ~десятки событий/с против ~1900/с на локальном стенде — и что́
> именно это ограничивает. Сеть networkID 1338, chainId 0x1869f, BatchMappingWMS на subnet-EVM.
> Работа измерительная: каждый вывод подкреплён прямым замером (consensus-метрики avalanchego,
> WAN-RTT, профиль газа, бенчмарк ядра/диска VPS), а не оценкой.
>
> **Этот документ уточняет throughput-числа из `geo-distributed-report.md`:** тот отчёт корректно
> фиксирует отказоустойчивость (kill-1-of-3) и 0 потерь; здесь — разбор самого́ потолка скорости.

## Резюме

| Вопрос | Измеренный ответ |
|---|---|
| Узкое место — газ? | **Нет.** gasLimit 200M, реальный gasUsed ≤0.1% в простое / ≤80% в бёрстах, base fee на полу (25 gwei, плоский). Запас ~30×. |
| Узкое место — сеть/WAN? | **Нет.** RTT между валидаторами 10–46 мс (ping). Финализация — не сетевая задержка. |
| Узкое место — число ядер? | **Нет.** EVM однопоточный: транзакции блока исполняются последовательно. Больше ядер сборку блока не ускоряет. |
| Узкое место — сырая ёмкость цепи / число signer'ов? | **Нет.** Adapter-bypass blast (8 и 24 signer'а, прямой замер блоков): бёрст-финализация **≥4.2M газ/с (200 tx/с) = 2.07× среднего**, пик-блок 2000 tx / 21% лимита. 3× signer'ов устойчивый темп не подняли (только пиковую упаковку — упаковка ≠ throughput). Средние ~100 tx/с — submission-bound артефакт бластера, не потолок. |
| Узкое место — адаптер? | **Было (краш), починено.** Подробности ниже. |
| Узкое место — **конфиг (кэши/swap)?** | **ДА, частично — и это чинится настройкой.** Кэши subnet-evm были сконфигурированы больше доступной RAM → ~800 МБ swap на **вращающийся HDD** → сборка блока распухала. Ужатие кэшей (trie 64/64 + snapshot 32) уронило `build_block` в **6.1×/4.8×** (8.95→~1.5 с dino, 24.0→~5.0 с alex) — чистой сменой настроек, без замены железа. |
| **Что упирается после фикса** | Сборка блока **больше не узкое место** (~1.5–5 с ≪ наблюдаемый каденс ~19 с). Остаточный каденс согласуется с накладными WAN-консенсуса/ProposerVM (poll ~1.25 с, ~27% poll-fail, форки) — цена гео-распределения. Разница build между узлами (dino vs alex) — железный пол одного ядра/диска. |
| Устойчивость под нагрузкой (PACE=50, кэш-фикс) | backlog пик **20860 → монотонно в 0**, **0 FAILED**, integrity held — burst-absorption без потерь |
| Тот же стек, адекватное железо (локально) | 1924 события/с |

**Вывод одной строкой:** «потолок» оказался **в значительной мере чинимой ошибкой конфигурации**
(кэши subnet-evm > RAM → swap на HDD → сборка блока 9–24 с); ужатие кэшей уронило `build_block`
в 4.8–6.1× **чистой настройкой, без смены железа**. Остаток — накладные WAN-консенсуса и железный
пол одного ядра/диска, а не протокол, газ или сеть. Всё измерено, а не предположено.

## Постановка вопроса

Локальный стенд (subnet-EVM, 2-секундные блоки) выдавал 1924 события/с. Гео-сеть из тех же
компонентов давала порядок ~100/с и периодически роняла адаптер. Рабочая гипотеза была
«поднять газ до предела». Задача — измерить, что́ реально ограничивает, и не гадать.

## Стенд и методология

- **Цепочка:** 3 валидатора avalanchego v1.14.0 + subnet-evm на VPS с 1 ядром
  (🇲🇩 dino, 🇷🇴 alex, 🇳🇱 itldc), консенсус snow `sample=3 / quorum=2`, stake-weighted BFT.
  Наблюдательная RPC-нода `node-home` (за NAT) обслуживает чтения адаптера.
- **Нагрузка:** изолированный `stresstest`-стек (postgres с OLTP-тюнингом, Kafka, Debezium,
  WMS, ledger-adapter), репойнтнутый на гео-цепь через `deploy/geo/run-app-on-geo.sh`.
  k6 в режиме `constant-arrival-rate` гонит реальный складской поток
  приёмка→раскладка→сборка→отгрузка по HTTP API.
- **Путь события:** WMS → `outbox_events` → Debezium CDC → ledger-adapter (батч, multi-signer)
  → subnet-EVM.
- **Инструментовка (ключевое для «не гадать»):**
  - `deploy/geo/metrics/consensus-collect.sh` — on-box-сборщик snowman/meterchainvm-метрик с
    валидаторов: `blks_accepted`, `poll_duration`, `polls_failed`, `blks_polls_rejected`,
    `meterchainvm_build_block`. Дельта за окно прогона даёт per-block декомпозицию.
  - WAN-RTT — `ping` между публичными IP валидаторов.
  - Профиль газа — `eth_getBlockByNumber` (gasUsed/gasLimit/baseFeePerGas по блокам).
  - Бенчмарк ядра/диска VPS — однопоточный счётный цикл + `dd ... conv=fdatasync`.

## Что НЕ является узким местом (измерено)

### Газ
Genesis: `gasLimit=200000000` (200M, против 8M по умолчанию subnet-evm), `targetBlockRate=1`,
`minBaseFee=25 gwei`. FeeManager-precompile выключен. Замеры по блокам:

| Состояние | gasUsed/блок | % лимита | baseFeePerGas |
|---|---|---|---|
| Простой | ~71 000 | <0.1% | 25 gwei (пол) |
| Под нагрузкой (бёрст) | 99–160M | до 80% | **25 gwei (плоский!)** |

База комиссии **не растёт** даже в бёрстах (адаптер платит 525 gwei — ×21 над полом), значит
цепочка не считает себя перегруженной по газу; запас ёмкости ~30×. **Поднимать газ бессмысленно**,
а изменить gasLimit без FeeManager-precompile можно только пересозданием цепи на 3 VPS — ради
метрики, которая не лимитирует. «Газ до талого» отброшено замером.

### Сеть / WAN
RTT между валидаторами (ping): dino↔alex **10 мс**, dino↔itldc **46 мс**, alex↔itldc **31 мс**.
Один раунд BFT-консенсуса — десятки миллисекунд; даже 20 раундов дали бы ~1 с. Наблюдаемые
десятки секунд на блок — **не сетевая латентность**.

### Число ядер
EVM однопоточный по построению: транзакции внутри блока исполняются строго последовательно
(каждая может читать стейт, изменённый предыдущей). Поэтому **добавление ядер не ускоряет ни
сборку, ни верификацию блока** — это не распараллеливаемая работа. Второе ядро даёт лишь
второстепенный выигрыш (развести потоки консенсуса/сети/прочих чейнов avalanchego от
единственного EVM-exec-потока + параллельный prefetch стейта на верификации).

### Сырая ёмкость цепи (adapter-bypass blast)

Чтобы отделить ёмкость самой цепи от пути доставки (Kafka→Debezium→adapter), цепь нагружена
**в обход адаптера**: пул из 8 и 24 независимых signer'ов лил дешёвые 21k-газ переводы прямо в
mempool, блоки 1064–1099 разобраны постфактум через `eth_getBlockByNumber` напрямую с валидатора
(:9650, не через node-home).

| Прогон | sustained (средн.) | пик-блок | каденс |
|---|---|---|---|
| 8 signers (BURST=16) | 2.15M газ/с, 102 tx/с | 784 tx, 16.5M газ (8% лимита) | 2.8 с/блок |
| 24 signers (BURST=8) | 2.03M газ/с, 96 tx/с | **2000 tx, 42M газ (21% лимита)** | 6.1 с/блок |

Два прочтения, и важно их не путать:

- **Средний rate — submission-bound, НЕ потолок цепи.** 3× signer'ов не сдвинули средний темп
  (102→96 tx/с): оба прогона лили через единственную relay-ноду node-home и `cast send --async`
  (subprocess-на-tx с ноутбука) — упёрлись в путь подачи, а не в цепь. Поэтому ~100 tx/с — артефакт
  бластера, и **выносить его как «потолок» нельзя** (та же дисциплина, что и с ev/s).
- **Сырая ёмкость цепи — в разы выше, доказана бёрст-окном.** Когда mempool забит (~5000),
  размер блока отражает не темп подачи, а сколько цепь *вытягивает и финализирует*: блоки 1094→1096
  дали **75.6M газ за 18 с = 4.20M газ/с (200 tx/с) — 2.07× среднего**; densest шаг 1095→1096 =
  6.72M газ/с. Пик-блок — 2000 tx / 21% gasLimit. То есть у цепи ≥2× запас над средним бластером,
  и сырая пропускная способность — **не** узкое место.

Единственное, на что повлияло число signer'ов, — **пиковая упаковка блока** (784→2000 tx/блок):
больше независимых nonce-потоков → больше одновременно-валидных tx в одном блоке. Упаковка ≠
throughput; гипотеза «добавить signer'ов → выше устойчивый TPS» замером **не подтвердилась**.

> **Зачем это здесь.** Bypass убирает адаптер/CDC из контура: раз цепь и без них финализирует
> ≥4.2M газ/с в бёрстах, узкое место устойчивого режима — не сырая ёмкость цепи и не адаптер как
> relay, а (а) сборка блока на 1 ядре (починена кэшами) + (б) каденс WAN-консенсуса и ожидание
> receipt'ов на тяжёлых recordMovement-tx (режим адаптера, см. ниже). Согласуется с PACE-замерами.

## Что является узким местом (измерено)

**Сборка/верификация блока на одном ядре — НО распухшая неверной настройкой кэшей (см. ниже
контр-эксперимент).**

Дельта consensus-метрик за окно нагрузки (прогон с переуплотнением, блоки ~2000 событий,
**ДО кэш-фикса**):

| Метрика | dino (МД) | alex (РО) |
|---|---|---|
| **build_block** (VM строит блок, 1 ядро) | **8.95 с** | **24.0 с** |
| poll_duration (валидатор верифицирует блок перед голосом) | 1.52 с | 4.55 с |
| cadence | 31.6 с/блок | 34.3 с/блок |

Прямой бенчмарк самих VPS подтверждает, что дело в скорости коробки:

| Узел | Ядра / модель | Однопоточный цикл | Диск (fdatasync) | build/блок |
|---|---|---|---|---|
| dino | 1 / QEMU Virtual CPU 2.5+ | 4.46 с | 227 MB/s | 9 с |
| alex | 1 / QEMU Virtual CPU 2.5+ | **8.15 с** | **95 MB/s** | **24 с** |
| Mac M1 Max (локальный «1924/с») | 10 / NVMe | быстрое ядро | NVMe (≫1 GB/s) | — |

**Связь линейная и доказательная:** alex медленнее dino и по ядру (8.15 vs 4.46 с), и по диску
(95 vs 227 MB/s) — и строит блок 24 с против 9 с. Гео-узлы — дешёвые oversold QEMU-vCPU
(«Virtual CPU version 2.5+» — древняя абстрактная модель), медленное ядро и медленный диск.

**Реконсиляция 1924/с (локально) vs гео:** код один, EVM один, протокол один. Часть разницы —
скорость ядра/диска (M1 Max + NVMe против 1-vCPU + диск 95–227 MB/s). Но эти 9–24 с **не были
чистым железом**: значительная их доля — чинимая ошибка конфигурации (кэши subnet-evm больше RAM
→ swap на HDD). Контр-эксперимент ниже показывает, что ужатие кэшей роняет сборку блока в 4.8–6.1×
**без смены железа**, а после фикса узким местом становится уже не сборка блока.

## Решающий контр-эксперимент: настройки vs железо

Вопрос «насколько правда влияет железо — может, настройки неверные?» проверен прямым замером.
Гипотеза: 9–24 с на сборку — не чистая скорость ядра, а **swap-thrashing**. На осмотре узлов
обнаружено: кэши subnet-evm (`trie-clean` + `trie-dirty` + `snapshot`) суммарно ~1.8 ГБ при
**1.4 ГБ RAM** на боксе → ~0.8 ГБ постоянного swap, причём раздел подкачки — на **вращающемся HDD**
(`ROTA=1`, 95–227 МБ/с). Сборка блока трогает trie, не помещающийся в кэш → промах идёт в swap на
HDD → секунды на блок.

**Фикс — чисто настройка**, без касания железа. На каждый валидатор положен
`/etc/avalanchego/chains/<BID>/config.json`:

```json
{"trie-clean-cache":64,"trie-dirty-cache":64,"snapshot-cache":32,"metrics-expensive-enabled":false}
```

Swap после ужатия (прямой замер `free`): dino **777→146 МБ**, alex **796→238 МБ**.

**Тот же прогон (PACE=50, window=8, batch=300, multi-signer) на тех же VPS, изменены только кэши:**

| build_block (Δsum/Δcount за окно) | dino (МД) | alex (РО) |
|---|---|---|
| ДО кэш-фикса (run5) | 8.95 с | 24.0 с |
| ПОСЛЕ кэш-фикса | **~1.5 с** | **~5.0 с** |
| **Ускорение (raw)** | **6.1×** | **4.8×** |

Падение в 4.8–6.1× получено **сменой одной настройки на неизменном железе** — то есть значительная
доля «потолка» была чинимой ошибкой конфигурации, а не свойством бюджетных VPS. Даже с поправкой на
несколько меньший размер блока в этом прогоне (~1347 событий/блок против ~2000 ранее; вторая цифра
приблизительная) per-1000-событий сборка всё равно падает в **3–4×** (dino 4.5→1.1 с, alex
12.0→3.7 с). _Оговорка: build_count в окне = 4 (dino) / 8 (alex) блоков, поэтому «~1.5 с» —
порядок, а не точное значение._

**После фикса узким местом стала уже не сборка блока.** Сборка (~1.5–5 с) теперь существенно ниже
наблюдаемого каденса (~19 с/блок, бёрстами), что **согласуется** с тем, что доминирующей стоимостью
становятся накладные WAN-консенсуса/ProposerVM (poll ~1.25 с, ~27% poll'ов без кворума, форки) —
цена самого гео-распределения. _Механизм каденса в этом прогоне не изолирован: 19 с считаны по всем
23 блокам включая пост-нагрузочный дренаж, а build_block — по первым ~8–11 блокам (коллектор
остановился раньше); привести как точную причинность нельзя._

**Эффект на устойчивость (бесспорная часть).** При том же предложенном темпе 50/с цепь с кэш-фиксом
**удержала нагрузку без потерь**: backlog поднялся до пика **20860** и **монотонно сошёл в 0**,
**0 FAILED**, integrity held — burst-absorption без потери событий. (Конкретное число «событий/с»
сознательно не выносится в заголовок: единица k6 — итерация, не событие, а каденс бёрстовый; надёжный
наблюдаемый факт — нулевые потери и полный дренаж очереди, а не точный rate.)

**Итог контр-эксперимента:** разделение «настройки vs железо» теперь измерено. Чинимая настройка
(кэши/swap) давала 3–6× инфляции сборки блока; после её устранения остаются (а) накладные
WAN-консенсуса как цена гео-распределения и (б) разница одного ядра/диска между узлами как железный
пол. Вывод «исключительно железо» опровергнут собственным замером.

## Бистабильность: почему «потолок» был обманчив

Система бистабильна по предложенному темпу. При перегрузке адаптер накапливает backlog, и каждый
блок «захватывает» гигантскую очередь (~2000 событий) → 1 ядро строит его 9–24 с → каденс падает
до ~30 с → это выглядит как «потолок ~100/с». При темпе ≤ ёмкости блоки мелкие и быстрые.

| Предложенный темп | Очередь | Итог |
|---|---|---|
| **PACE=15 (~30 ev/s)** | **ограничена, дренаж до 0** | sustained 31/с, integrity TRUE, **0 потерь**, polls-fail 0%, каденс 3.5–7.4 с |
| PACE=40 (~80 ev/s) | убегает | sustained 24/с (деградация), блоки распухают |
| PACE=50–100 (overdrive) | убегает + краши | ~100–130/с gross, но latency 60–100 с, build 9–24 с/блок |

«~100–130/с», фигурировавшее в ранних прикидках, — это **transient burst-drain в режиме больших
блоков** (цепочка столько коммитит, но очередь и задержка растут неограниченно), **а не
устойчивая пропускная способность**. Подъём окна адаптера (8→32) ухудшает ситуацию — раскручивает
спираль (блоки реже, 45–101 с). Устойчивый режим — мелкие блоки при умеренном темпе.

## Декомпозиция консенсуса (вторичные эффекты)

Под перегрузкой, помимо медленной сборки, измерены: 22–31% poll'ов без кворума (ретраи) и
~1 отклонённый форк на каждый принятый блок. **Это следствие медленной сборки**, не отдельная
причина: пропозер на 1 ядре не успевает за слот ProposerVM → остальные строят конкурирующий блок
→ форк → раунды впустую. При умеренном темпе (мелкие блоки) poll-failures падают до 0%, форки
снижаются. Снижение consensus-параметра β (snow-commit-threshold) рассматривалось как рычаг и
**отклонено**: доминирует build_block, а изменение consensus-параметра на живой BFT-сети
рискованно (вплоть до остановки субсети).

> **Честная оговорка.** Произведение «polls/block × poll_duration» **не аддитивно** и не равно
> каденсу (poll'ы пайплайнятся/перекрываются) — его нельзя приводить как «время финализации».
> Надёжный сигнал — `build_block`. Доли форков/poll-failures приводятся как направление, а не
> точные значения (цепь прогонялась многократно подряд, что их завышает).

## Адаптер: реальный баг и его устранение

Под нагрузкой адаптер коллапсировал (committed=0), и это была **единственная починаемая кодом**
причина. `RECEIPT_POLL_TIMEOUT` по умолчанию 30 с был меньше реального WAN-каденса блоков (бёрсты
раз в 25–100 с, холодный первый блок ~33 с): первый же медленный блок → receipt timeout →
`pipeline stalled` → выход consumer'а → (без restart policy) контейнер мёртв → весь прогон в ноль.

Устранено (ветка `feature/geo-distributed-nodes`, всё собрано/протестировано):

- `6d464c31` — multi-signer ProductID-шардинг + параллельное подтверждение receipt'ов (semaphore 16).
- `b04805af` — потолок pipeline-окна масштабируется с числом signer'ов; исправлен неверный
  комментарий «gas-bound ~3 tx/блок» (он был про локальную цепь 8M, не про гео 200M).
- `aa80502f` — **главный фикс:** `restart: unless-stopped` + `RECEIPT_POLL_TIMEOUT=120s`
  (+ `RECONCILE_MIN_AGE=180s`, инвариант minAge>timeout) в geo-app override.

Результат: committed пошёл с нуля, адаптер ловит stall и **сам восстанавливается** (reconcile-loop
добивает домайненные за downtime транзакции), **0 потерь при любой нагрузке**.

## Рычаги для повышения TPS (по убыванию отдачи, измеримо-обоснованные)

1. **Ужать кэши subnet-evm под реальную RAM узла** (`trie-clean/dirty`, `snapshot`) — **проверено,
   бесплатно, без смены железа:** убрало swap на HDD и уронило `build_block` в 4.8–6.1×. Первое, что
   делать на любом RAM-ограниченном валидаторе. По возможности — `state-scheme=path` + вынести swap
   с вращающегося диска.
2. **Быстрее одно ядро + NVMe-диск на валидаторах** (premium/dedicated-vCPU, не многоядерный
   бюджетный). Сокращает остаточный железный пол build/verify после фикса кэшей.
3. **Держать темп ≤ ёмкости** (offered ≤ drain) — мелкие блоки, быстрый каденс, 0 потерь;
   не сваливаться в режим больших блоков.
4. ~~Газ / окно адаптера / β консенсуса / число signer'ов~~ — измеренно **не помогают** (окно
   вверх — хуже; signer'ы 8→24 устойчивый темп не подняли, только пиковую упаковку блока — см.
   adapter-bypass blast выше).

## Вывод для ВКР

Гео-распределённый блокчейн-слой работает корректно: реальный BFT-консенсус через WAN в 3 странах,
отказоустойчивость (потеря 1 из узлов — без потерь), сквозная целостность WMS↔chain, **0 потерь**.
Изначально наблюдавшийся «потолок» (сборка блока 9–24 с) оказался **в значительной мере чинимой
ошибкой конфигурации**: кэши subnet-evm были больше RAM узла → swap на вращающийся HDD. Ужатие
кэшей — **чистая настройка, без смены железа** — уронило `build_block` в 4.8–6.1× и сняло сборку
блока с позиции узкого места; под той же нагрузкой цепь удержала поток без потерь (backlog
20860 → 0, 0 FAILED). Остаточные ограничения — накладные WAN-консенсуса (цена гео-распределения)
и разница одного ядра/диска между узлами (железный пол); на адекватном железе тот же стек даёт
1924/с. Это сильнее «голого числа»: замерами разделено, что́ чинится настройкой, что́ — цена
гео-распределения, а что́ — железо. Для складского контура (единицы событий/с) измеренная ёмкость
кратно избыточна.

## Воспроизводимость

- Прогон: `deploy/geo/run-geo-bench.sh` (env: `PACE_RPS`, `PACE_DURATION`, `FAULT`,
  `ADAPTER_BATCH_SIZE`, `ADAPTER_PIPELINE_WINDOW`, `PRIVATE_KEYS`).
- Consensus-инструментовка: `deploy/geo/metrics/consensus-collect.sh` (on-box, дельта за окно).
- Multi-signer фондинг: `deploy/geo/fund-signers.sh`. Adapter-bypass blast: пул signer'ов льёт
  21k-газ переводы в mempool; ёмкость считается постфактум по `eth_getBlockByNumber` **напрямую с
  валидатора (:9650)** — node-home :9750 под нагрузкой замораживает height (relay-лаг), его CSV для
  throughput непригодны. Дискриминатор A/B — бёрст-окно (забитый mempool), а не средний rate
  (он submission-bound).
- **Кэш-фикс валидатора:** `chain-config-dir: /etc/avalanchego/chains` в node-config +
  `/etc/avalanchego/chains/<BID>/config.json` = `{"trie-clean-cache":64,"trie-dirty-cache":64,`
  `"snapshot-cache":32,"metrics-expensive-enabled":false}`; рестарт узла. Проверка эффекта — `free`
  (swap до/после) и `build_block` из consensus-CSV. **Гоча:** rolling-restart на баре-кворуме 2/3 —
  рестартить по одному и ждать `healthy`, иначе субсеть встаёт (видели halt при рестарте 2-го узла,
  пока 3-й был unhealthy; BFT-safety удержал, голова восстановилась за ~240 с на HDD).
- Фиксы адаптера: коммиты `6d464c31`, `b04805af`, `aa80502f`.
- Гочи окружения: Kafka CLI требует `-e JMX_PORT= -e KAFKA_JMX_OPTS= -e KAFKA_OPTS=` (порт JMX
  занят брокером); `timeout` отсутствует на macOS; consensus-CSV забирать чистым `cat` (не `pkill;cat`).
