Методология

Что именно измерялось

Нагрузка подаётся k6-харнессом (tests/stress/09-throughput.js) в режиме constant-arrival-rate: реальный складской поток приёмка → раскладка → сборка → отгрузка по HTTP API WMS на устойчивом темпе 8 итер/с в течение 7m. WMS пишет события в outbox → Debezium CDC → ledger-adapter батчует и отправляет on-chain. Метрики снимаются двумя независимыми потоками: из БД (коммиты, очередь, задержка, целостность) и напрямую с каждого узла (consensus-высота, пиры, RSS, CPU через /ext/metrics). Все запросы к БД оконены отметкой начала прогона.

Честная оговорка о задержке. Величина «задержка коммита» = updated_at − created_at строки on-chain-события: это сквозная задержка пайплайна (ожидание батча + отправка + опрос receipt), а не чистое время финализации консенсуса. Финализация субсети — порядка одного блока.

Устойчивая пропускная способность

Фронт поглощает нагрузку, очередь полностью слилась

k6-фронт прошёл 3,361 итераций с отказами HTTP всего 0.07% — WMS поглощает поток (outbox развязывает фронт от цепочки). Цепочка устойчиво коммитит ~27.2 событий/с; в этом прогоне предложенный темп слегка превысил эту ёмкость, поэтому очередь outbox постепенно росла (пик 3,569) и затем полностью слилась до 0 — всплеск выше ёмкости поглощён без потери уже закоммиченных событий. Склад генерирует единицы событий/с, так что измеренная ёмкость кратно перекрывает реальную потребность.

Отказоустойчивость · kill-1-of-3

Отказ узла под живой нагрузкой

Консенсус. Пока alex был выключен, валидаторы финализировали (высота субсети +18 блок(ов)).

Пайплайн — выстоял. С 4 валидаторами потеря одного оставляет 75 % > порога 73.33 %, поэтому observer-нода node-home осталась healthy и не замёрзла (продвинулась на 19 блок(ов) — против ~0 в 3-нодовой конфигурации); под отказом закоммичено 1356 событий, 0 потеряно — никаких receipt-таймаутов, double-submit и реверзов.

Деградация изящная. WAN-финализация при выключенном узле замедлилась (p99 задержки подрос, backlog временно вырос), но полностью слился за 191 с; отгрузки сошлись (2478 = 2478). Closed-loop подтверждение, что 4-й валидатор устраняет лимит 3-нодовой конфигурации.

Вывод. С 4 валидаторами потеря 1 узла оставляет 75 % > 73.33 %: observer не замерзает, пайплайн коммитит под отказом, 0 потерь. Лимит 3-нодовой конфигурации (отдельный отчёт geo-3node-before) закрыт добавлением валидатора — closed-loop before→after. Запас тонкий (75 % vs 73.33 % ≈ 1.7 п.п.): сильное многонодовое WAN-разделение могло бы снова просадить observer ниже порога — но это уже отказ 2+ узлов, а не одного.
