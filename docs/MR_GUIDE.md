## Перед созданием MR

### 1. Убедись что ветка по конвенции

```bash
# Правильно
feature/receiving-endpoint
fix/kafka-timeout
docs/api-reference

# Неправильно
my-branch
FIX-something
```

> Подробнее: [docs/CONVENTIONS.md](./CONVENTIONS.md#git-именование-веток)

### 2. Убедись что коммиты по конвенции

```bash
# Проверить последние коммиты
git log --oneline -5

# Каждый коммит должен быть в формате:
# feat(wms): добавить handler приёмки товаров
# fix(ledger-adapter): обработать ошибку таймаута
```

> Подробнее: [docs/CONVENTIONS.md](./CONVENTIONS.md#git-сообщения-коммитов)

### 3. Прогони проверки локально

```bash
# Линтинг
make lint

# Тесты
make test

# Или всё через pre-commit
make hooks-run
```

### 4. Убедись что Docker-сборка работает

```bash
make build
make ps  # все контейнеры healthy
```

## Шаблон MR

Шаблон подставляется автоматически при создании MR в GitLab.

Файл шаблона: [`.gitlab/merge_request_templates/Default.md`](../.gitlab/merge_request_templates/Default.md)

Если создаёшь MR через CLI (`git push -o merge_request.create`), скопируй шаблон вручную:

```markdown
## Что сделано

<!-- Краткое описание изменений. 2-3 предложения. -->

## Зачем

<!-- Какую проблему решает? Ссылка на issue если есть. -->

## Тип изменений

- [ ] Новая функциональность (feat)
- [ ] Исправление бага (fix)
- [ ] Рефакторинг (refactor)
- [ ] Документация (docs)
- [ ] Тесты (test)
- [ ] CI/CD (ci)
- [ ] Другое (chore)

## Затронутые модули

- [ ] wms/internal/receiving
- [ ] wms/internal/assembly
- [ ] wms/internal/putaway
- [ ] wms/internal/shipping
- [ ] wms/internal/platform
- [ ] wms/internal/ledger
- [ ] ledger-adapter
- [ ] deploy / docker-compose
- [ ] миграции БД
- [ ] CI

## Как проверить

<!-- Пошаговая инструкция для ревьюера. -->

1. `docker compose up -d --build`
2. `curl http://localhost:8080/health`
3. Ожидаемый результат: `{"status": "ok", ...}`

## Скриншоты / Логи

<!-- Если применимо — вставь скриншот или вывод команды. -->

## Чеклист автора

- [ ] Код соответствует [конвенциям](./CONVENTIONS.md)
- [ ] Все коммиты в формате Conventional Commits
- [ ] `make lint` проходит без ошибок
- [ ] `make test` проходит
- [ ] Docker-сборка работает (`make build`)
- [ ] Если есть миграции — есть down-миграция
- [ ] Документация обновлена (если нужно)
```

## Правила оформления

### Размер MR

| Размер | Строк кода | Оценка | Рекомендация |
|--------|-----------|--------|-------------|
| XS | < 50 | Отлично | — |
| S | 50-200 | Хорошо | — |
| M | 200-500 | Нормально | Постарайся разбить |
| L | 500-1000 | Плохо | Разбей на 2-3 MR |
| XL | > 1000 | Очень плохо | Разбей обязательно |

**Правило:** один MR = одна логическая задача. Не мешай фичу с рефакторингом.

### Заголовок MR

Формат совпадает с Conventional Commits:

```
feat(wms): добавить API приёмки товаров
fix(ledger-adapter): обработать таймаут подключения к ноде
docs: описать API эндпоинты
```

### Описание MR

- **Что** — что конкретно изменилось (файлы, модули)
- **Зачем** — зачем это нужно (проблема → решение)
- **Как проверить** — пошагово, чтобы ревьюер мог воспроизвести

### Draft MR

Если работа ещё в процессе — создай Draft MR:
- В GitLab: поставь `Draft:` перед заголовком
- Это позволяет получить раннюю обратную связь
- НЕ назначай ревьюеров на Draft

## Чеклист ревьюера

При ревью проверяй по порядку:

### 1. Формальное

- [ ] Заголовок и коммиты по конвенции
- [ ] Описание заполнено (что, зачем, как проверить)
- [ ] Размер адекватный (< 500 строк)
- [ ] Нет мусорных файлов (.DS_Store, .env, vendor/)

### 2. Архитектура

- [ ] Код в правильном модуле (receiving ≠ shipping)
- [ ] Зависимости однонаправленные (handler → service → repo)
- [ ] Нет горизонтальных зависимостей между модулями
- [ ] Новые типы в `domain/` если используются в 2+ модулях

### 3. Код

- [ ] Ошибки обрабатываются и оборачиваются (`fmt.Errorf("context: %w", err)`)
- [ ] Нет `_ = fn()` для функций возвращающих error
- [ ] Нет хардкода конфигов — всё через env / config
- [ ] SQL-запросы параметризованы (`$1, $2`) — без конкатенации строк
- [ ] Контексты прокидываются (`ctx context.Context`)

### 4. Тесты и сборка

- [ ] CI пайплайн зелёный
- [ ] Если новый эндпоинт — есть хотя бы один тест
- [ ] Docker-сборка не сломалась

### Как оставлять комментарии

```
# Блокирующий (нужно исправить):
🔴 Ошибка не обрабатывается — добавь проверку err

# Не блокирующий (рекомендация):
🟡 Можно упростить через strings.Builder, но не критично

# Вопрос:
🔵 Почему тут не используем транзакцию?

# Похвала (тоже важно):
🟢 Отличная декомпозиция, чисто
```

## Частые ошибки

### 1. "Мега-MR"

**Проблема:** MR на 2000 строк с фичей + рефакторингом + фиксом бага.

**Решение:** Разбивай. Сначала MR с рефакторингом, потом MR с фичей.

### 2. "Пустое описание"

**Проблема:** Заголовок `update` и пустое описание.

**Решение:** Используй шаблон выше. Описание — уважение к ревьюеру.

### 3. "Коммит-каша"

**Проблема:** 15 коммитов `fix`, `fix2`, `wip`, `asdasd`.

**Решение:** Перед MR сделай `git rebase -i` и объедини в логические коммиты:
```bash
git rebase -i develop
# Помечай 'squash' или 'fixup' для мусорных коммитов
```

### 4. "Конфликты"

**Проблема:** MR нельзя смержить из-за конфликтов.

**Решение:** Перед созданием MR:
```bash
git fetch origin
git rebase origin/develop
# Разреши конфликты если есть
git push --force-with-lease
```

> `--force-with-lease` безопаснее чем `--force` — не перезапишет чужие изменения.

### 5. "Забыл миграцию"

**Проблема:** Код ожидает новую колонку в БД, но миграции нет.

**Решение:** Если меняешь схему — ВСЕГДА добавляй миграцию (up + down).
